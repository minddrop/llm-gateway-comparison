# 日本向けマルチクラウド LLM ゲートウェイ アーキテクチャ比較（AWS / Azure / GCP）

> **対象範囲:** 本書はアーキテクチャのみを扱う（実装コードは含まない）。**LiteLLM Proxy** を基盤とする社内 LLM ゲートウェイ プラットフォームを説明する。このプラットフォームは、ユーザー・チーム管理、コスト配賦、トークン制御を提供する。各設計は当社の環境に合わせている。ID 基盤は **Microsoft Entra ID**、MFA は **Okta Verify**、デバイス信頼は **Microsoft Intune**、閉域接続は既設の **ExpressRoute / Direct Connect / Cloud Interconnect** であり、本設計ではこれを任意の経路として扱う。利用者は社内ネットワーク上のエンジニアで、Claude Code などの AI コーディング エージェントを含む。リモート・在宅からのアクセスはこのフェーズの対象外とする [A-13]。
>
> **データ所在地: 日本国内のみ。** 本ゲートウェイは日本の利用者向けである。モデル推論、ゲートウェイ処理、ログ、データ パイプライン（利用額エクスポート、請求エクスポート、分析）はすべて日本国内に閉じなければならない。そのため各設計は日本のリージョン（東京をプライマリ、大阪を DR）だけを使い、処理が日本国内に閉じるモデル デプロイ方式だけを使う。ルールと現時点のモデル提供状況は [§2.5](01-common-design.md#25-日本国内データ所在全設計に適用) を参照。
>
> **ステータス:** アーキテクチャ レビュー用ドラフト（2026-11-04 時点、接続経路モデルとクライアント認証を改訂）。ベンダーの機能は変化が速い。ベンダー固有の記述にはすべて公式ドキュメントへのリンクを付けているので、最終決定の前にリンク先を再確認すること。
>
> **翻訳について:** 本書は英語版（[`docs/en/`](../en/00-overview.md)）の日本語訳である。各ファイルは英語版と同じファイル名で対応している。内容に差異がある場合は英語版を正とする。サービス名・機能名・設定キーは原則として英語表記のままとしている。

## 0. エグゼクティブ サマリー

- **どのクラウドでも LiteLLM が制御点になる。** LiteLLM は仮想キー、組織／チーム／ユーザー／キーの階層、予算、TPM/RPM 制限、モデル アクセス グループ、利用額ログを管理する。その周囲のクラウド ネイティブ サービスが、LiteLLM にない機能を補う。具体的には、エッジと WAF、プライベート ネットワーク、マネージド Postgres と Redis、シークレット、ガードレール、ログ、請求の突合である。
- **ID の構成は 3 クラウドで同一である。** Entra ID を LiteLLM の唯一の OIDC/SAML IdP とする。Okta Verify は Entra ID の **外部認証方法（External Authentication Method, EAM）** として接続するため、単一の条件付きアクセス エンジンが MFA と **Intune デバイス コンプライアンス** の両方を評価する。クラウド間で異なるのは、各クラウドのコントロール プレーンを Entra ID とどうフェデレーションするかだけである。
- **ユーザーは Entra が、デバイスは Intune が識別し、LiteLLM が両方を適用する。** クラウド事業者自身のサービスがエンド ユーザーを識別することはない。WAF はネットワーク上の送信元を、ロード バランサーは Intune デバイス証明書を確認でき（推奨オプション）、LiteLLM が Entra トークンを検証してユーザーをチームに対応付ける（[§2.3.1](01-common-design.md#231-リクエストごとに誰が何を検証するか)）。
- **既定は Entra トークン。仮想キーは貼り付けたキーが必要なツールだけ。** Entra の条件付きアクセス、つまり Intune コンプライアンスが確認されるのは Entra がトークンを *発行するとき* だけである。当社がサポートする公式 CLI である **Claude Code と Codex CLI** は、どちらもコマンドを実行して資格情報を取得するので、約 1 時間ごとに新しい Entra トークンを得て、そのたびにデバイスが再確認される（[§2.3.4](01-common-design.md#234-コーディング-エージェントのクライアント)）。LiteLLM の **仮想キー** は作成後に Entra の目に触れないベアラー シークレットなので、コマンドを実行できない IDE プラグインやツールだけに、有効期限 30〜90 日で発行する。すべてのリクエストは **オフィス／DC の送信元 IP 許可リスト** も通る。
- **Intune 証明書による mTLS は推奨オプションであり、場合によっては必須になる（[§2.3.2](01-common-design.md#232-ロード-バランサーで-mtls-が確認すること)）。** 当社の送信元 IP を共有する管理対象外デバイスで、コピーされた仮想キーが使われるのを止められる唯一の制御である。利用者の設定は不要で、秘密鍵はエクスポート不可でなければならない。管理対象外デバイスが当社の送信元 IP に到達できる場合 [A-16]、リモート アクセスを追加する場合 [A-13]、JWT 認証なしで運用する場合 [A-6] は必須になる。証明書のユーザーとキーの所有者の照合は **採用しない**（[§2.3.3](01-common-design.md#233-証明書とユーザーの紐付け-採用しない)）。
- **クラウド アカウントへの運用者アクセスには専用の制御が必要である（[§2.9](01-common-design.md#29-アクセス-シナリオとチェックポイント)）。** AWS コンソールと CLI はゲートウェイの WAF の背後にない。専用の条件付きアクセス ポリシー（CA-GW-05: フィッシング耐性のある MFA、準拠デバイス、オフィス／DC のネームド ロケーション）、クラウド IAM の送信元 IP 条件、1 時間の管理者セッションでこの経路を守る。
- **接続経路: まず公開経路を 1 本、専用線は任意（[§2.6](01-common-design.md#26-接続経路モデル全設計に適用)）。** 主経路の **経路 B** では、オフィスのクライアントがインターネット経由で東京のリージョナル ロード バランサーに接続する。WAF は当社の送信元 IP だけを許可し、mTLS を採用する場合はロード バランサーが Intune 証明書を、LiteLLM が Entra トークンまたは仮想キーを検証する。**経路 A** は任意で、同じゲートウェイを内部ロード バランサーの背後に置き、Direct Connect、ExpressRoute、Interconnect 経由で接続する。どちらの経路も ID とデバイスの確認は同じなので、経路 A が加えるのは分離であって認証ではない。ゲートウェイの前段に **CDN やグローバル エッジ**（CloudFront、Front Door、Google のグローバル外部ロード バランサー）は **置かない**。LLM の応答はキャッシュできず、これらのエッジは日本国外で通信を復号しうるうえ、タイムアウトが長いモデル応答には短すぎる。
- **日本国内の所在要件は、何よりもモデルの選択肢を狭める（[§2.5](01-common-design.md#25-日本国内データ所在全設計に適用)）。** どのクラウドにも推論を日本国内で処理する方式はあるが、いずれもグローバル方式より対象モデルが少ない。AWS では Bedrock の `jp.` 地理的推論プロファイル（東京 ↔ 大阪）、Azure では Japan East の Standard と Regional Provisioned デプロイ、GCP では `asia-northeast1` リージョン エンドポイントがそれにあたる。GCP で日本国内処理として掲載されている Gemini モデルはごく一部である。グローバル方式と複数国にまたがる方式（Bedrock の `global.`/`apac.`、Azure の Global と Data Zone、Vertex の `global` エンドポイント）はポリシーで禁止する。インターネット経由の直接のモデル API（OpenAI、Anthropic など）も、プロバイダーが日本国内処理を契約で約束しない限り禁止する。
- **推奨（詳細は [§7](06-comparison.md#7-ステップ-3-比較と推奨)）:** プライマリ ゲートウェイは **AWS 東京に置き、大阪を DR リージョンとする。** Bedrock の `jp.` プロファイルは、日本国内で処理されるフロンティア モデルの品ぞろえが最も広く、日本の両リージョンから利用できる。LiteLLM ベースのサンプルを公開しているのも AWS だけである。接続経路と実行環境の判断は [sample-litellm-bedrock-gateway-on-eks](https://github.com/aws-samples/sample-litellm-bedrock-gateway-on-eks) に従う（[§3.1](02-reference-architectures.md#31-aws)）。ただしギャップが 1 つ残る。Bedrock Guardrails の日本語対応（Standard 階層）のチェックは APAC 全域にルーティングされるため、ガードレールは VPC 内で実行する必要がある。OpenAI モデルが必要なら、**Japan East の Azure OpenAI Standard デプロイ** を 2 つ目の LiteLLM バックエンドとして追加し、日本国内の閉域経路で接続する。GCP は、日本国内処理に対応した少数の Gemini モデルで足りる場合にのみ適する。
- **可搬性:** LiteLLM はどのクラウドでも同じ方式（コンテナー、Postgres、Redis）でデプロイする。そうすればゲートウェイを移設でき、他クラウドの日本リージョンのモデルも LiteLLM のバックエンドとして追加できる。
- **専用線（ステップ 4）は任意（経路 A）である。** 閉域経路はトラフィックを分離するだけである。それ自体はユーザーもデバイスも認証せず、何も暗号化しないため、経路 A でも経路 B の制御をすべて維持する。構築する価値があるのは特定の契機がある場合だけである。オフィスのプロキシでゲートウェイを TLS インスペクションの対象外にできない、社内システムのインターネット公開エンドポイントがポリシーで禁止されている、送信ファイアウォールが固定の宛先 IP しか許可できない、インターネット ブレイクアウトの容量が足りない、のいずれかである（[§8.0](07-private-connectivity.md#80-経路-a-を採用すべき場合)）。

## 1. 前提条件

当社環境の詳細が不明な点について、本設計は以下を前提とする。各前提には **[A-n]** の番号を付け、本書全体で参照する。

| ID | 前提 | 重要な理由／確認方法 |
|---|---|---|
| A-1 | Entra ID が全従業員の正規の IdP であり、すべてのユーザーがクラウド同期済みの UPN とグループ メンバーシップを持つ（オンプレミス AD からの同期、またはクラウド専用）。 | OIDC クレームと LiteLLM のチーム同期を左右する。 |
| A-2 | Okta は **MFA プロバイダーとしてのみ** 使用する（Okta Verify のプッシュ、TOTP、または FastPass）。M365 のプライマリ フェデレーション IdP では **ない**。採用パターン: **Entra ID 外部認証方法（EAM）**（[§2.1](01-common-design.md#21-okta-verify-と-entra-id-の統合パターン) 参照）。 | 実際には M365 ドメインが *Okta にフェデレーション* されている場合は、[§2.1.2](01-common-design.md#21-okta-verify-と-entra-id-の統合パターン) の代替パターンを使う。 |
| A-3 | Entra ID P1/P2 ライセンス（条件付きアクセス、グループ クレーム、アプリ ロール）がある。Intune が Windows と macOS、必要に応じて iOS/Android のデバイス コンプライアンスを適用している。 | 「準拠デバイスを必須にする」条件付きアクセスには P1 以上が必要。 |
| A-4 | ユーザーは社内ネットワーク上の Intune 管理デバイスのブラウザーから LiteLLM 管理 UI にアクセスする。API クライアントには公式のコーディング CLI（**Claude Code、Codex CLI**）、IDE プラグイン、SDK、社内アプリ、そして **オンプレミス DC またはクラウドで稼働する AI エージェント** が含まれる。 | クライアント種別ごとの認証方式を決める（[§2.3](01-common-design.md#23-litellm-api-トラフィックの認証方式)）。 |
| A-5 | **日本国内のみ。** プライマリ リージョンは東京（AWS `ap-northeast-1`、Azure Japan East、GCP `asia-northeast1`）、ウォーム スタンバイの DR リージョンは大阪（AWS `ap-northeast-3`、Azure Japan West、GCP `asia-northeast2`）とする。すべてのモデル呼び出し、ゲートウェイの構成要素、ログ保存先、バックアップ、データ パイプラインをこれらのリージョンに閉じる。 | モデルの選択肢が大きく制限される。[§2.5](01-common-design.md#25-日本国内データ所在全設計に適用) のスナップショットを参照し、モデルを追加するたびに再確認すること。 |
| A-6 | **LiteLLM Enterprise ライセンス** を購入する。現行ドキュメントでは、6 ユーザー以上の SSO、OIDC/JWT 認証、SCIM、監査ログ、一部のガードレール・ログ連携がエンタープライズ機能である。 | ライセンスがない場合、6 ユーザー以上の SSO と JWT 認証は使えない。[LiteLLM Enterprise](https://docs.litellm.ai/docs/enterprise) と [Admin UI SSO](https://docs.litellm.ai/docs/proxy/admin_ui_sso) を参照。 |
| A-7 | インターネット上の外部モデル プロバイダー（例: OpenAI API、Anthropic API）は、日本国内で処理されることを示せないため **既定で禁止** する。法務とセキュリティが日本国内での処理と保存を書面で確認した場合にのみ追加できる。他クラウドのモデルは、その日本リージョンで日本国内処理されるものに限って許可し、できるだけ日本国内の閉域経路で接続する。 | 送信許可リスト、ルーターのフォールバック、ステップ 4 に影響する。 |
| A-8 | 既設の ExpressRoute、Direct Connect、Interconnect 回線は、ランディング ゾーンのスポークと接続済みのハブ／トランジット ネットワークで終端している。いずれも 2 拠点に 2 回線以上ある。ゲートウェイがこれらを使うのは、経路 A を採用する場合か、他クラウドの日本リージョン バックエンドに接続する場合だけである。 | ステップ 4 の可用性の主張に影響する。ネットワーク チームに確認し、経路 A を採用する前に帯域と契約条件をプロバイダーに確認すること。 |
| A-9 | サイジング検討用の想定規模: 従業員約 5,000 人、ピーク時の同時ユーザー約 300 人、ゲートウェイ経由で約 50〜200 RPS（ストリーミング応答あり）。 | コスト要因の議論にのみ使う。価格は提示しない。 |
| A-10 | 既定では、プロンプトと応答の **内容** は保存 *しない*。メタデータ（ユーザー、チーム、モデル、トークン数、コスト、レイテンシ、ガードレール判定）のみを記録する。内容のログ記録は、コンプライアンス用途に限りチーム単位のオプトインとする。 | プライバシーと保持期間の設計を左右する（[§4.7](03-aws.md#47-データとログaws)、[§5.7](04-azure.md#57-データとログazure)、[§6.7](05-gcp.md#67-データとログgcp)）。 |
| A-11 | 所在要件の対象は、**プロンプト、補完、埋め込み、およびそれらから派生するすべてのデータ**（利用額ログ、リクエスト メタデータ、トレース、ガードレール結果、バックアップ、分析用コピー）である。SaaS の ID コントロール プレーン（Entra ID、Okta、Intune）は ID データを処理するがプロンプトは扱わないため、対象外とする。各クラウド事業者自身の請求・計測システムも対象外で、当社が制御するのは請求エクスポートの保存先だけである。 | この範囲を法務とプライバシー担当部署に確認すること。ID データも日本国内に置く必要がある場合、それは Entra/Okta のテナント所在地の問題であり、本設計では解決できない。 |
| A-12 | プロバイダーの不正利用監視は、その保存先が日本国内であれば許容する。承認済みの顧客が人によるレビュー用の保存を無効化できる場合（Azure の *modified abuse monitoring*）は申請する。 | [§2.5](01-common-design.md#25-日本国内データ所在全設計に適用) を参照。日本国外からのプロバイダー側の人によるレビューを許容するかは法務が判断する。 |
| A-13 | **利用者は社内ネットワーク上にいる。** ゲートウェイの利用者はオフィスで働くエンジニアと、オンプレミス DC およびクラウドのワークロードである。リモート・在宅からのアクセスはこのフェーズの対象外とする。 | 経路 B でオフィス／DC の IP 許可リストを使えるのはこの前提による。後でリモート アクセスを追加する場合は、許可リストを ZTNA（例: Entra Private Access）に置き換えるか、mTLS と Entra だけに頼る（[§8.6](07-private-connectivity.md#86-リモート-ワーカーとハイブリッド-ワーカー)）。 |
| A-14 | オフィスと DC のインターネット ブレイクアウトは、少数の安定したパブリック送信元 IP（NAT）を使っており、WAF とロード バランサーの許可リストに登録できる。 | ネットワーク チームに確認すること。送信元 IP を変更する場合は、先に許可リストを更新しないと利用者が締め出される。 |
| A-15 | 社内のセキュア Web ゲートウェイで `llm.corp.example` を TLS インスペクションの対象外にでき、送信ファイアウォールで FQDN 単位に許可できる。 | TLS インスペクションは mTLS を壊し、プロキシがプロンプトとキーを読めるようにしてしまう。どちらかができない場合は、固定 IP のフロントエンドか経路 A が必要になる（[§2.6](01-common-design.md#26-接続経路モデル全設計に適用)）。 |
| A-16 | **管理対象外デバイスはオフィスや DC の送信元 IP から外に出られない。** ゲスト／BYOD ネットワークは許可リストにない別の送信元 IP を使い、社内の LAN と Wi-Fi は管理対象デバイスだけを受け入れる（802.1X/NAC）。 | これが成り立たない、または誰も確認できない場合、IP 許可リストは管理対象デバイスを意味しないので、コピーされた仮想キーが管理対象外デバイスから使われないよう **mTLS が必須になる**（[§2.3.2](01-common-design.md#232-ロード-バランサーで-mtls-が確認すること)）。ネットワーク チームと確認する。 |
