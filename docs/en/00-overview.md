# Multi-Cloud LLM Gateway Architecture Comparison for Japan (AWS / Azure / GCP)

> **Scope:** This document covers architecture only (no implementation code). It describes an internal LLM gateway platform built on **LiteLLM Proxy**. The platform provides user and team management, cost allocation, and token controls. Each design is built for our environment: **Microsoft Entra ID** for identity, **Okta Verify** for MFA, **Microsoft Intune** for device trust, and existing **ExpressRoute / Direct Connect / Cloud Interconnect** links, which these designs treat as an optional route. The users are engineers on the corporate network, including AI coding agents such as Claude Code. Remote and home access is out of scope for this phase [A-13].
>
> **Data residency: Japan only.** The gateway serves users in Japan. Model inference, gateway processing, logs, and data pipelines (spend exports, billing exports, analytics) must all stay in Japan. Each design therefore uses only Japanese regions (Tokyo primary, Osaka for DR) and only model deployment options that keep processing in Japan. See [§2.5](01-common-design.md#25-japan-data-residency-applies-to-every-design) for the rules and the current model availability.
>
> **Status:** Draft for architecture review, as of 2026-11-04 (ingress model and client authentication revised). Vendor features change quickly. Every vendor claim links to official documentation, and you should check those links again before you make a final decision.

## 0. Executive summary

- **LiteLLM is the control point on every cloud.** It owns virtual keys, the org/team/user/key hierarchy, budgets, TPM/RPM limits, model access groups, and spend logs. The cloud-native services around it supply what LiteLLM lacks: an edge and WAF, private networking, managed Postgres and Redis, secrets, guardrails, logging, and billing reconciliation.
- **Identity is the same on all three clouds.** Entra ID is the only OIDC/SAML IdP for LiteLLM. Okta Verify is attached to Entra ID as an **External Authentication Method (EAM)**, so a single Conditional Access engine evaluates both MFA and **Intune device compliance**. The clouds differ only in how their own control planes federate with Entra ID.
- **Entra identifies the user, Intune identifies the device, and LiteLLM enforces both.** The cloud providers' own services never identify the end user. The WAF checks the network origin, the load balancer can check an Intune device certificate (recommended option), and LiteLLM validates the Entra token and maps the user to a team ([§2.3.1](01-common-design.md#231-who-verifies-what-on-each-request)).
- **Entra tokens by default; virtual keys only where a tool needs a pasted key.** Entra Conditional Access, and therefore Intune compliance, is checked only when Entra *issues* a token. The official CLIs we support, **Claude Code and Codex CLI**, both run a command to fetch their credential, so they get a fresh Entra token about every hour and the device is re-checked each time ([§2.3.4](01-common-design.md#234-coding-agent-clients)). LiteLLM **virtual keys** are bearer secrets that Entra never sees again after they are created, so they are only for IDE plugins and tools that cannot run a command, with a 30–90 day expiry. Every request also passes the **office/DC egress IP allowlist**.
- **mTLS with Intune certificates is a recommended option, and required in some cases ([§2.3.2](01-common-design.md#232-what-mtls-checks-at-the-load-balancer)).** It is the only control that stops a copied virtual key from working on an unmanaged device that shares our egress IP. Users do nothing to set it up, and the private key must be non-exportable. It becomes required if unmanaged devices can reach our egress IPs [A-16], if remote access is added [A-13], or if we run without JWT auth [A-6]. Matching the certificate's user to the key's owner is **not adopted** ([§2.3.3](01-common-design.md#233-certificateuser-binding-not-adopted)).
- **Operator access to the cloud accounts needs its own controls ([§2.9](01-common-design.md#29-access-scenarios-and-checkpoints)).** The AWS console and CLI do not sit behind the gateway's WAF. A dedicated Conditional Access policy (CA-GW-05: phishing-resistant MFA, compliant device, office/DC named locations), source-IP conditions in cloud IAM, and 1-hour admin sessions cover that path.
- **Ingress: one public route first, the private line optional ([§2.6](01-common-design.md#26-ingress-model-applies-to-every-design)).** On **Route B**, the primary route, clients in the office reach a regional load balancer in Tokyo over the internet. The WAF allows only our egress IPs, the load balancer verifies the Intune certificate if mTLS is adopted, and LiteLLM verifies the Entra token or virtual key. **Route A** is optional: the same gateway behind an internal load balancer, reached over Direct Connect, ExpressRoute, or Interconnect. Both routes apply the same identity and device checks, so Route A adds isolation, not authentication. **No CDN or global edge** (CloudFront, Front Door, Google's global external load balancer) sits in front of the gateway. LLM responses cannot be cached, those edges can decrypt traffic outside Japan, and their timeouts are too short for long model responses.
- **Japan residency narrows the model choice more than anything else ([§2.5](01-common-design.md#25-japan-data-residency-applies-to-every-design)).** Every cloud has an option that processes inference in Japan, but each one covers fewer models than its global option. On AWS that option is the Bedrock `jp.` geographic inference profiles (Tokyo ↔ Osaka). On Azure it is the Standard and Regional Provisioned deployment types in Japan East. On GCP it is the `asia-northeast1` regional endpoint, and only a handful of Gemini models are listed with in-Japan processing. Global and multi-country options (Bedrock `global.`/`apac.`, Azure Global and Data Zone, the Vertex `global` endpoint) are blocked by policy. Direct internet model APIs (OpenAI, Anthropic, and others) are blocked unless the provider contractually commits to processing in Japan.
- **Recommendation (detail in [§7](06-comparison.md#7-step-3-comparison-and-recommendation)):** Put the primary gateway on **AWS Tokyo, with Osaka as the DR region**. Bedrock's `jp.` profiles give the widest set of frontier models processed in Japan, and both Japanese regions can serve them. AWS is also the only cloud with published LiteLLM samples. We follow [sample-litellm-bedrock-gateway-on-eks](https://github.com/aws-samples/sample-litellm-bedrock-gateway-on-eks) for ingress and runtime decisions ([§3.1](02-reference-architectures.md#31-aws)). One gap remains: Bedrock Guardrails routes Japanese-capable (Standard tier) checks across APAC, so guardrails must run inside the VPC. If OpenAI models are required, add **Azure OpenAI Standard deployments in Japan East** as a second LiteLLM backend, reached over a private path inside Japan. GCP fits only if the few Gemini models with in-Japan processing are enough.
- **Portability:** deploy LiteLLM the same way on every cloud (containers, Postgres, Redis), so the gateway can move and other clouds' Japan-region models can be added as LiteLLM backends.
- **Dedicated lines (Step 4) are optional (Route A).** A private path only isolates traffic. It does not authenticate users or devices, and it does not encrypt anything by itself, so Route A keeps every Route B control. It is worth building only on a specific trigger: the office proxy cannot exempt the gateway from TLS inspection, policy forbids internet-facing endpoints for internal systems, the egress firewall can only allow fixed destination IPs, or internet breakout capacity is a problem ([§8.0](07-private-connectivity.md#80-when-route-a-is-worth-adopting)).

## 1. Assumptions

Where our environment details are unknown, these designs assume the following. Each one is marked **[A-n]** and referenced throughout the document.

| ID | Assumption | Why it matters / how to validate |
|---|---|---|
| A-1 | Entra ID is the authoritative IdP for all employees, and every user has a cloud-synced UPN and group membership (synced from on-premises AD or cloud-only). | Drives OIDC claims and LiteLLM team sync. |
| A-2 | Okta is used **only as the MFA provider** (Okta Verify push, TOTP, or FastPass). It is **not** the primary federation IdP for M365. Pattern chosen: **Entra ID External Authentication Methods (EAM)** (see [§2.1](01-common-design.md#21-okta-verify--entra-id-integration-patterns)). | If our M365 domains are actually *federated to Okta*, use the alternative pattern in [§2.1.2](01-common-design.md#21-okta-verify--entra-id-integration-patterns). |
| A-3 | Entra ID P1/P2 licensing is in place (Conditional Access, group claims, app roles). Intune enforces device compliance for Windows and macOS, and for iOS/Android where needed. | Conditional Access with "require compliant device" needs P1 or higher. |
| A-4 | Users reach the LiteLLM admin UI from a browser on an Intune-managed device on the corporate network. API clients include the official coding CLIs (**Claude Code, Codex CLI**), IDE plugins, SDKs, internal apps, and **AI agents hosted in the on-premises DC or in the cloud**. | Determines the authentication mode per client type ([§2.3](01-common-design.md#23-authentication-modes-for-litellm-api-traffic)). |
| A-5 | **Japan only.** The primary region is Tokyo (AWS `ap-northeast-1`, Azure Japan East, GCP `asia-northeast1`), and the warm-standby DR region is Osaka (AWS `ap-northeast-3`, Azure Japan West, GCP `asia-northeast2`). Every model call, gateway component, log store, backup, and data pipeline stays in these regions. | This limits model availability heavily. See the snapshot in [§2.5](01-common-design.md#25-japan-data-residency-applies-to-every-design), and re-check it before each model is onboarded. |
| A-6 | We buy a **LiteLLM Enterprise license**. In current docs, SSO for more than 5 users, OIDC/JWT auth, SCIM, audit logs, and some guardrail and logging integrations are enterprise features. | Without the license, SSO for more than 5 users and JWT auth are unavailable. See [LiteLLM Enterprise](https://docs.litellm.ai/docs/enterprise) and [Admin UI SSO](https://docs.litellm.ai/docs/proxy/admin_ui_sso). |
| A-7 | External model providers on the internet (for example the OpenAI API or the Anthropic API) are **not allowed by default**, because we cannot show that they process requests in Japan. A provider can be added only after legal and security confirm in-Japan processing and storage in writing. Other clouds' models are allowed only from their Japanese regions, with in-Japan processing, and preferably over a private path inside Japan. | Affects the egress allowlist, the router fallbacks, and Step 4. |
| A-8 | The existing ExpressRoute, Direct Connect, and Interconnect circuits terminate in a hub/transit network that is already peered with landing-zone spokes. Each has at least 2 circuits at 2 locations. The gateway uses them only if Route A is adopted, or for cross-cloud Japan-region backends. | Affects HA claims in Step 4. Validate with the network team, and confirm bandwidth and contract terms with the provider before adopting Route A. |
| A-9 | Expected scale for sizing discussions: about 5,000 employees, about 300 concurrent users at peak, and roughly 50–200 RPS through the gateway with streaming responses. | Used only to discuss cost drivers. No pricing is quoted. |
| A-10 | By default, prompt and response **content** is *not* stored. Only metadata (user, team, model, tokens, cost, latency, guardrail verdict) is logged. Content logging is a per-team opt-in for compliance use cases. | Drives the privacy and retention design ([§4.7](03-aws.md#47-data--logging-aws), [§5.7](04-azure.md#57-data--logging-azure), [§6.7](05-gcp.md#67-data--logging-gcp)). |
| A-11 | The residency requirement covers **prompts, completions, embeddings, and everything derived from them** (spend logs, request metadata, traces, guardrail results, backups, analytics copies). It does not cover the SaaS identity control plane (Entra ID, Okta, Intune), which processes identity data but never prompts. Each cloud provider's own billing and metering systems are also out of scope; we control only where billing exports land. | Confirm this scope with legal and the privacy office. If identity data must also stay in Japan, that is a separate Entra/Okta tenant-location question that this design cannot solve. |
| A-12 | Provider abuse monitoring is acceptable if its storage stays in Japan. Where a provider lets approved customers turn off human-review storage (Azure *modified abuse monitoring*), we apply for it. | See [§2.5](01-common-design.md#25-japan-data-residency-applies-to-every-design). The legal team decides whether provider-side human review from outside Japan is acceptable. |
| A-13 | **Users are on the corporate network.** The gateway serves engineers working from our offices, plus workloads in the on-premises DC and in the cloud. Remote and home access is out of scope for this phase. | Makes the office/DC IP allowlist on Route B possible. If remote access is added later, replace the allowlist with ZTNA (for example Entra Private Access) or rely on mTLS + Entra alone ([§8.6](07-private-connectivity.md#86-remote-and-hybrid-workers)). |
| A-14 | Office and DC internet breakouts use a small, stable set of public egress IPs (NAT) that we can list in the WAF and load-balancer allowlist. | Validate with the network team. Any change to egress IPs must update the allowlist first, or users are locked out. |
| A-15 | The corporate secure web gateway can exempt `llm.corp.example` from TLS inspection, and the outbound firewall can allow it by FQDN. | TLS inspection breaks mTLS and lets the proxy read prompts and keys. If either is impossible, use a fixed-IP front end or Route A ([§2.6](01-common-design.md#26-ingress-model-applies-to-every-design)). |
| A-16 | **Unmanaged devices cannot leave through the office or DC egress IPs.** Guest and BYOD networks use separate egress IPs that are not on the allowlist, and the corporate LAN and Wi-Fi admit only managed devices (802.1X/NAC). | If this does not hold, or nobody can confirm it, the IP allowlist does not imply a managed device, and **mTLS becomes required** so that a copied virtual key cannot be used from an unmanaged device ([§2.3.2](01-common-design.md#232-what-mtls-checks-at-the-load-balancer)). Validate with the network team. |
