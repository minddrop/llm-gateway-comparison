# 7. Step 3: Comparison and recommendation

## 7.1 Side-by-side comparison

Ratings: ●●● = strongest / lowest effort, ●○○ = weakest / highest effort. Ratings compare the three designs for *our* environment under the **Japan-only residency requirement** ([§2.5](01-common-design.md#25-japan-data-residency-applies-to-every-design)). They are not general rankings.

| Dimension | AWS (Tokyo + Osaka) | Azure (Japan East + Japan West) | GCP (`asia-northeast1` + `asia-northeast2`) |
|---|---|---|---|
| **Models processed in Japan** *(the deciding factor)* | ●●● `jp.` profiles cover current frontier Claude models (Opus 5.5, Haiku 5.5, Opus 4.8, Sonnet 4.6, Haiku 4.5) and Nova 2 Lite. Some models are In-Region in Tokyo (Mistral Large 3, gpt-oss-120b, embeddings). Several newest models (for example Claude Sonnet 5.5) are Global-only and therefore blocked. | ●●○ Only `Standard` and `ProvisionedManaged` in Japan East. Microsoft says geography-based types "arrive last" with "no guaranteed availability date", so expect fewer and older models than Global offers. | ●○○ Only a few Gemini models are listed with in-Japan processing (3.5 Flash, 2.5 Flash 128k, 2.5 Pro 64k) plus embeddings. No partner models (Claude, Mistral) and nothing for Osaka. |

Self-hosted in-VPC guardrails are needed (more build and run effort). | ●●● Content Safety and Prompt Shields in Japan East, with Japanese-trained harm classifiers. ## 7.2 Recommendation

1. **Build one LiteLLM gateway platform design that is portable across clouds** and restricted to Japanese regions: containers + PostgreSQL + Redis, Entra OIDC/JWT, the LiteLLM tenancy model in [§2.4](01-common-design.md#24-litellm-tenancy-model-same-on-all-clouds), the residency rules in [§2.5](01-common-design.md#25-japan-data-residency-applies-to-every-design), and IaC modules per cloud. Pick **one primary hosting cloud**, and reach other clouds' **Japan-region** models as LiteLLM backends over the private lines.
2. **Primary hosting: AWS Tokyo, with Osaka as DR.** Under Japan-only processing, AWS has the broadest set of frontier models processed in Japan, a model layer that keeps working from Osaka, and the only LiteLLM-based samples. Start from the EKS sample in ECS mode and apply the changes in [§4](03-aws.md#4-step-2a-aws-design):
   - Use Entra SSO and JWT auth (the sample uses virtual keys only). Claude Code and Codex CLI fetch Entra tokens with a token command; virtual keys are only for tools that accept a pasted key ([§2.3.4](01-common-design.md#234-coding-agent-clients)).
   - Keep the sample's ingress: ALB only (no CloudFront), security group limited to our office/DC egress IPs, 600 s timeouts. Add ALB mTLS with Intune certificates as a recommended option, required if [A-16] does not hold ([§2.3.2](01-common-design.md#232-what-mtls-checks-at-the-load-balancer)). Do not add a certificate/user match ([§2.3.3](01-common-design.md#233-certificateuser-binding-not-adopted)).
   - Protect operator access: CA-GW-05 on the IAM Identity Center app, `aws:SourceIp` conditions, and 1 h admin permission sets ([§2.9](01-common-design.md#29-access-scenarios-and-checkpoints)).
   - Tune the WAF's Core rule set for LLM bodies ([§2.7](01-common-design.md#27-waf-tuning-and-timeouts-for-llm-traffic)).
   - Send egress through Network Firewall, with no model FQDNs allowed.
   - Reach Bedrock only through VPC endpoints.
   - Tag application inference profiles that are copied from `jp.` profiles, instead of the sample's `global.`/`us.` examples.
   - Set `store_prompts_in_spend_logs: false` ([§2.8](01-common-design.md#28-who-can-see-prompts)).
   - Add a region-deny SCP.
   - Run guardrails in the VPC, because Bedrock Guardrails is not Japan-only for Japanese content. Budget for building and running them.
3. **Ingress: Route B first, Route A only on a trigger ([§2.6](01-common-design.md#26-ingress-model-applies-to-every-design)).** Build the public route with the office/DC IP allowlist and Entra JWT, plus mTLS where [§2.3.2](01-common-design.md#232-what-mtls-checks-at-the-load-balancer) requires or recommends it, on whichever cloud hosts the gateway. Do not put a CDN or global edge in front of it. Add the private-line route only if a trigger in [§8.0](07-private-connectivity.md#80-when-route-a-is-worth-adopting) applies; it adds isolation but no identity or device protection.
4. **If OpenAI models are required, add Azure OpenAI Japan East (Standard / Regional Provisioned) as a second backend.** Reach it over Direct Connect → the Tokyo colocation router → ExpressRoute private peering, so the traffic stays in Japan. Use the Azure Content Safety resource in Japan East as its guardrail. **Choose Azure as the primary host instead** if OpenAI is the main model family and Japan East already offers the required models as Standard. Azure then also gives the best Japan-resident guardrails and the tightest Entra/Intune integration.
5. **Use GCP only for a narrow Gemini use case** that the Japan-listed models cover. Claude on Vertex and most Gemini models are not processed in Japan, and Vertex has no model DR inside Japan.
6. **Don't stack API managers by default.** APIM or Apigee in front of LiteLLM duplicates token accounting. Add them only for a specific need, such as shared PTU pooling across non-LiteLLM consumers, or a corporate API portal mandate.
7. **Treat LiteLLM spend as the allocation key and cloud billing as the cost truth.** Run a monthly reconciliation job on every cloud, in Japan. If Route A or cross-cloud backends use the private lines, allocate the gateway's share of their cost ([§8.9](07-private-connectivity.md#89-private-connectivity-cost-japan)) as platform overhead.
8. **Re-check the Japan model snapshot every quarter and before onboarding any model.** Model availability per region and per deployment type changes faster than this document.

## 7.3 Key trade-offs

| Trade-off | Implication |
|---|---|
| Japan-only processing vs. the newest models | New models often launch as Global or multi-country options first. For example, Claude Sonnet 5.5 is Global-only from Tokyo, and Azure geography-based deployments "arrive last". Teams will sometimes wait months for a model. Do not grant exceptions through `global.` profiles, Global deployments, or public APIs; route the request to the residency owner instead. |
| Self-hosted guardrails (AWS) vs. managed guardrails (Azure / GCP) | On AWS we own the guardrail models, their Japanese accuracy, scaling, and patching. Azure Content Safety in Japan East and Model Armor in Tokyo are managed but exist only in the primary region. |
| LiteLLM as the single policy point vs. cloud-native gateway (APIM/Apigee) | LiteLLM gives one user/team/budget model across all providers. It is open source, and the enterprise features need a license. Our team owns patching and scaling, so pin versions and track LiteLLM security advisories. |
| Virtual keys (simple) vs. Entra JWT (zero-trust) | Virtual keys work with every tool, but they are bearer secrets with no device check at use time. JWTs re-apply Conditional Access every token lifetime, but need a token command. Claude Code and Codex CLI both support one, so use JWT by default. Issue virtual keys only for tools that accept a pasted key, with expiry, behind the office/DC IP allowlist, and behind mTLS where [A-16] does not hold. |
| mTLS with Intune certificates vs. no client certificates | mTLS is the only per-request device check, and the only thing that stops a copied virtual key on an unmanaged device inside the office. Its cost is on the client side: a TLS-inspection exemption, non-exportable keys, and CLIs that read certificates only as files (Claude Code) or not at all (Codex CLI), which needs a local mTLS helper. Recommended; required if [A-16] does not hold, remote access is added, or JWT auth is unavailable. |
| Route B (internet) vs. Route A (private line) | Both carry the same TLS and the same identity and device checks. Route B depends on the office proxy exemption and stable egress IPs; Route A depends on the carrier contract, circuit bandwidth, DC routing, and DNS forwarding, and removes the public endpoint. Start with Route B; add Route A only on a trigger ([§8.0](07-private-connectivity.md#80-when-route-a-is-worth-adopting)). |
| Single cloud host vs. multi-cloud active/active | Multi-cloud hosting gives provider-outage resilience but doubles ops and needs cross-cloud budget consistency (shared Postgres is not practical). Prefer single-cloud HA across Tokyo and Osaka, plus a cold-standby IaC on a second cloud's Japanese regions. |
| Content logging vs. privacy | Logging prompts helps abuse investigation and quality work, but creates a sensitive data store that must also stay in Japan. Default to metadata only [A-10], and allow opt-in per team with separate keys and retention. |
| Managed serverless containers vs. Kubernetes | Fargate, ACA, and Cloud Run minimize ops. Kubernetes is needed for sidecars (Presidio), custom ingress, GPU-hosted guardrail models, or self-hosted models. |
