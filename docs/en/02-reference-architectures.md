**Ways to combine APIM with LiteLLM on Azure:**

1. **LiteLLM only (recommended default).** LiteLLM calls Azure OpenAI and Foundry models through private endpoints with managed identity. This avoids two token-accounting systems.
2. **LiteLLM → APIM → Azure OpenAI.** APIM acts as a *backend* pool manager. Use this if a central platform team already runs APIM for Azure OpenAI PTU sharing across many consumers. LiteLLM is then one APIM subscriber with its own `llm-token-limit`.
3. **APIM → LiteLLM.** APIM acts as the enterprise API front door for developer-portal publishing and products. Use this only if APIM is already the corporate API standard. It adds latency and cost, and duplicates policy.

> **Observation:** Only AWS publishes samples built **on LiteLLM** (two of them). Microsoft and Google publish gateway references built on their **own API-management products** (APIM, Apigee). For those two clouds, we take the *network, identity, and security baseline* from the official references and put LiteLLM in the gateway position.
>
> **Japan note:** none of these references is written for in-country residency. Adopt their topology, but check every model setting in their samples (the EKS sample's examples, for instance, all use `global.` or `us.` profiles). Global or multi-country options (Bedrock `global.`/`apac.` profiles, Azure Global and Data Zone deployments, the Vertex `global` endpoint) are blocked by [§2.5](01-common-design.md#25-japan-data-residency-applies-to-every-design).
